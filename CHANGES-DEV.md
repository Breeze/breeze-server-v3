# Breeze .NET Server v8 — developer change log

A running summary of structural changes, for people working **on** Breeze. Consumer-facing
changes are in [UPGRADE.md](./UPGRADE.md); current task state is in [STATUS.md](./STATUS.md).

---

## New repo

v8 lives in a new repo rather than a branch. `breeze.server.net` is untouched and keeps
serving 7.x. Only the five shipping packages and the tests that support them came across;
the four dead source trees (`AspNet`, `AspNetCore`, `AspNetCore-v3`, `Old` — 527 files) did
not.

Layout is `src/` / `tests/` / `tools/`, replacing `DotNet/` / `Tests/`. Project depth is
unchanged, so relative paths inside the `.csproj` files still resolve.

## Project files: 93 to 14

The old repo kept a separate `.csproj` per .NET version — `Breeze.Core.5.csproj`,
`.6.csproj`, `.7.csproj` alongside the real multi-targeting one, plus a stray
`Breeze - Backup.Core.csproj`, plus the same pattern across every test model project. Only
the multi-targeting files survive.

`src/Directory.Build.props` now holds everything that was duplicated five ways: version,
authors, copyright, licence, icon, README, packaging and target frameworks — and **one
`Breeze.snk` instead of five copies**. Each `.csproj` is down to about 15 lines carrying
only its assembly name, product, description and references.

`GeneratePackageOnBuild` is off. Pack explicitly with `dotnet pack`.

## Target frameworks

`net5.0;net6.0;net7.0;net8.0;net9.0;net10.0` becomes `net8.0;net9.0;net10.0`.

This halves the conditional `PackageReference` matrix in `Breeze.Persistence.EFCore` and
makes every preprocessor conditional in the shipping code unconditional. There are
surprisingly few — **6 regions, about 30 lines, across 3 files** in 9,735 lines:

| File | Regions | What |
|---|---|---|
| `Breeze.Core/Query/DataType.cs` | 2 | `DateOnly` / `TimeOnly` |
| `Breeze.Core/TypeFns.cs` | 1 | the same two types in a list |
| `Breeze.Persistence.EFCore/MetadataBuilder.cs` | 3 | `DistinctBy`, `Enum.GetValuesAsUnderlyingType`, and a 10-line `MetaTypeEqualityComparer` fallback that deletes outright |

The sprawl was never in the code — it was in the project files.

## UseArtifactsOutput — do not remove

Set in the **root** `Directory.Build.props`. `src/Directory.Build.props` chains to it
explicitly via `GetPathOfFileAbove`, because MSBuild imports only the nearest file.

Two host projects, `Test.AspNetCore.EFCore.csproj` and `Test.AspNetCore.NH.csproj`, share
one directory and one set of source files, switched by the `EFCORE` / `NHIBERNATE` compile
constants. That layout has two failure modes:

1. **Shared `obj/`.** A common `project.assets.json` means whichever project restored last
   wins, and the other silently loses its package references. This is why the NHibernate
   host failed to resolve `NHibernate` itself.
2. **Output under the project directory.** Each project excludes only *its own*
   `BaseIntermediateOutputPath` from the default compile glob, so it picks up the other's
   generated `AssemblyInfo.cs` and fails with duplicate assembly attributes.

Routing all output to a repo-root `artifacts/` tree fixes both. With it in place the whole
solution builds — NH host included, which it could not do in the old layout.

## Test server references local projects

`Test.AspNetCore.EFCore.csproj` referenced the published `Breeze.AspNetCore.NetCore` and
`Breeze.Persistence.EFCore` NuGet packages (7.5.0.1, resolving up to 7.5.1). It now uses
`ProjectReference` into `src/`, so the suite exercises the code in this repo.

## One test database

`NorthwindIB` + `InheritanceContext` + `ProduceTPH` become **`BreezeTestDb`**, 34 tables.
Their table names do not overlap, so the merge is clean. `Startup.cs` reads one connection
string.

**`InheritanceDbInitializer.Seed` no longer calls `EnsureDeleted`/`EnsureCreated`.** Against
a shared database that dropped the Northwind and Produce data on every server start. It
clears rows instead. Note that `EnsureCreated` is all-or-nothing per database and will not
add tables to an existing one, which is why the inheritance schema is a checked-in script
(`tests/Databases/inheritance-schema.sql`, generated from the EF model via
`GenerateCreateScript()`).

## Test data: 40MB of binaries becomes a 1.5MB script

`tests/Databases/BreezeTestDb.sql` — 33 tables, 235 schema statements, 4,108 data
statements — replaces the `.mdf`/`.ldf` files. Generated by the new `tools/DbScripter`
(SMO). Regenerate with:

```bash
dotnet run --project tools/DbScripter -- tests/Databases/BreezeTestDb.sql
```

Verified by rebuilding into an empty database: identical row counts on every table and
identical PK/FK/index/trigger/default counts. The only difference is `sysdiagrams`, an SSMS
artifact, deliberately excluded.

Practical wins: the script is diffable and reviewable, SQL Server creates the database
itself so there is no attach step and no file-permission workaround, and there is no silent
one-way file upgrade. The shipped `.mdf` was internal version 904 — SQL Server 2008 — and
attaching it to a modern instance upgraded it to 957 in place, dirtying the repo.

**Re-applying the script is also the reliable test reset.** `CleanBreezeTestDb.sql` cannot
restore the database: it misses `EmployeeID = 10`, leaves `Customer` at 95 against an
original 93, and one of its deletes fails with FK error `Msg 547`. A rebuild takes seconds.

## Doc warnings

`CS1591` (missing XML comment) is suppressed in `src/Directory.Build.props` — roughly 546
are missing and filling them in is its own task. Every other doc warning stays visible,
because those indicate *malformed* docs rather than absent ones. About 52 unique warnings
remain, all pre-existing; two invalid `<see cref="http://...">` URLs in
`NhQueryableInclude.cs` are already fixed.
